# Render deployment guide

This repository includes a Render Blueprint at the repository root. It defines two services:

- **finflow-api** — Node.js/Express API, built from the monorepo root.
- **finflow-web** — React/Vite static site, built and published from `frontend/dist`.

MongoDB remains on MongoDB Atlas. The Blueprint intentionally does not create, migrate, or modify a database.

## 1. Prepare MongoDB Atlas

1. Create or select an Atlas cluster in a region close to the Render API region (Singapore is the Blueprint default).
2. Create a dedicated database user with access only to the application's database.
3. Ensure the cluster is configured as a replica set; the app uses MongoDB transactions for payment records.
4. Add the Render API service's outbound IP ranges to the Atlas Network Access allowlist. Avoid a permanent `0.0.0.0/0` rule.
5. Copy the Atlas connection string and replace its database name with `fintech_smart_invoice` if needed.

## 2. Create the Blueprint

1. Open the [Render Dashboard](https://dashboard.render.com/).
2. Choose **New → Blueprint** and connect this GitHub repository.
3. Select the `main` branch and review the proposed resources before applying anything.
4. The Blueprint creates an API web service and a static frontend. It does not create a MongoDB database or send email.

The API service uses the existing root npm workspaces. Its build command compiles the backend, and its start command runs the compiled server. The static service builds the Vite app and publishes `frontend/dist`.

## 3. Set environment variables

Set these on the **finflow-api** service:

| Variable | Value |
| --- | --- |
| `NODE_ENV` | `production` (set by the Blueprint) |
| `MONGODB_URI` | Atlas connection string for the application database |
| `JWT_ACCESS_SECRET` | A unique random secret of at least 32 characters (generated by the Blueprint) |
| `CLIENT_URL` | Exact HTTPS origin of the deployed frontend, with no trailing slash |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM` | Optional; required for invoice email and overdue reminders |

Set this on the **finflow-web** static site:

| Variable | Value |
| --- | --- |
| `VITE_API_URL` | Full HTTPS origin of the deployed API, with no trailing slash |

The two public Render service URLs are assigned during service creation. After the first Blueprint sync, copy the actual URLs from the Render Dashboard and set `CLIENT_URL` and `VITE_API_URL` to those exact origins. Rebuild the frontend after changing `VITE_API_URL`, because Vite embeds it at build time. If the initial Blueprint flow asks for these values before the service URLs are visible, use temporary values only to complete the first creation, then replace them immediately and redeploy both affected services before testing sign-in.

Never commit real Atlas, JWT or SMTP credentials. Do not paste secrets into source control or project documentation.

## 4. Verify the staging deployment

1. Open `https://<api-service>.onrender.com/api/health`. It should return HTTP 200 with `status: "ok"` and `database: "connected"`.
2. Open the frontend URL and confirm the browser can load the API without CORS errors.
3. Register a normal Employee account, sign in, refresh the page, and verify the refresh-cookie session restores the session.
4. In a non-production test account, create a client, invoice and expense; verify invoice totals and due balances.
5. Record a small test payment and verify the invoice balance and audit event update together.
6. Verify the invoice PDF download. Test email only after SMTP has been configured.
7. Confirm the browser receives the refresh cookie with `HttpOnly`, `Secure` and the production SameSite settings.

Do not run test transactions against real customer or supplier records. Use a dedicated staging database and test accounts.

## 5. Scheduling and production caveats

The overdue reminder currently runs inside the API process using `node-cron`. It only runs while that process is alive. A free web service can spin down while idle, so it is not a reliable scheduler for production reminders. Use an always-on API plan or move reminder execution into a dedicated Render Cron Job/worker before relying on daily reminders.

The Blueprint is deployment configuration, not proof of a live deployment. A real rollout still requires Atlas credentials, exact frontend/API origins, optional SMTP credentials, a staging smoke test, and a security review. Do not enable production customer traffic until those checks pass.
